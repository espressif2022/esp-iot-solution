S31：present 取指停顿偏多，定位到哪里了

24项完整16场景缓存对照 · 第一轮链接顺序对照

已经证实：本轮差距受最终指令缓存布局显著影响，主要异常热点落在 LVGL 的4bpp字形位图转A8路径；不能直接归因为 present 像素处理量更多或 pixel worker 派发。
生产源码与IDF均未修改；下面全是独立诊断，原正式帧率／内存矩阵不替换。

1. 相同字体数据，只后移24字节

XIP关闭，800×480，DOUBLE_PARTIAL，单输入tile80000B，双方RGB bounce均10行。每组两次18秒全屏文字，预热约1秒；前后基线夹住干预。字体位图、glyph_dsc、cmaps、font_dsc共12个对象，以及font20描述符，地址保持不变；只增加24字节不执行的代码填充。

2. 时间主要差在哪个函数

每核1kHz中断PC采样，64字节分箱。以下是近似CPU驻留ms/渲染帧，多核相加；不是每函数miss计数，也不是单次调用耗时。分箱边界会使函数归属有误差。采样器全部位于IRAM，直读该镜像ELF验证的measuring标志地址，保留原probe，不插入热路径调用；逐镜像确认LVGL全局函数地址未改变。font＋24字节采样与该对照的字体数据／热函数地址一致。

3. 不能把跨缓存行直接等同于miss

同一段48字节4bpp内循环，四份最终ELF的循环机器码SHA256完全一致：

adapter和提前提取版本也跨两行，却更快。因此“跨两行就慢”不成立。已经有反事实实验证明的是整体链接排列改变了缓存表现；具体哪几组cache set／替换序列互相干扰，尚未通过硬件trace直接观测，不能据此宣称IDF缓存硬件bug。

4. 全局32字节对齐不是修复

对双方LVGL统一使用-fmin-function-alignment=32；在ELF中验证热点入口对齐。普通-falign-functions=64在-Os下被忽略，64字节最小函数对齐又触发当前干净IDF的链接区间冲突，未上板、未修改IDF。

5. 只把位图解包函数放进IRAM

应用级链接片段，对present和adapter完全相同：lv_font_fmt_txt:lv_font_get_bitmap_fmt_txt (noflash)，archive为liblvgl.a。函数最终1006字节，present的IRAM段增加约1012字节；不新增像素、tile、compose或传输缓冲，不改变扫描同步。它是代码放置优化，不表示整个字体绘制链路可在cache关闭时运行。

6. 对后续设计的含义

不能用某一份固件的总分直接推断present的层次／异步架构更慢：这里相同LVGL目标代码，只改变最终放置就出现显著波动。S31本轮每核16KiB指令缓存、64B行；Flash miss代价高，XIP已验证会显著降低每次补入的停顿代价，但不会使双方补入次数自动趋同。

应把扫描/像素后端成本和LVGL字体热点分开评估，回归中保留小幅链接扰动对照；针对已定位热函数使用小范围IRAM映射，比盲目全局对齐更可控。是否推广该映射，仍需以完整场景回归和IRAM预算决定。
