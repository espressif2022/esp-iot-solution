# S3 剩余吞吐问题：早期排查记录

后续已通过热路径内部 RAM 放置修复指定负载的吞吐差距，见 [最终修复与原版驱动 A/B](FB_IRAM_RESULTS_20261103.md)。下文保留找到有效方案前的阶段结论和被否定候选，不代表当前仍未修复。

## 结果

本轮没有找到同时保持当前调用／控制语义并恢复 V1 吞吐的补丁。生产源码保持 [ISR join 修复版](FB_ISR_JOIN_RESULTS_20261103.md)，S3 双 PARTIAL 仍约 30.29，双 DIRECT 的已归档基线仍为 56.12；没有把局部耗时下降或单轮较高成绩记作问题已修复。

全部候选在隔离副本中执行，未修改真实 IDF，也未合入生产路径。包括计时、缓存、任务调度、行数计算及标准 GDMA 原型的原始日志与统计在 [证据目录](evidence/s3-remaining-20261103/results.json)。所有实板轮次结束后均恢复原 flash 内容，并独立校验整片 16 MiB 与备份一致。

## 新增证据

1. 对既有诊断轨迹重算：双 PARTIAL 的 35 次提交中，没有完成回调落在 SUBMIT 到 ARM 的窗口内；DIRECT 有一次。因此 PARTIAL 剩余差距不能归结为提交／join 期间丢掉早到回调。
2. 新增 V1 同板、同配置计时。每轮均为 1800 次 tile 拷贝，对照仍可达到约 60 次／秒。V1 每帧逐行 memcpy 累计约 7.5 ms、tile 缓存写回约 7 ms；当前框架的 CPU 执行段计时约 17 ms。两者计时范围不同，均包含相应代码段被中断／调度抢占的时间，不能据此把差额归为某一个计算函数。
3. 当前行数解析函数内部计时只约 0.15 ms／帧，外层 API 时间明显更长。移除一层等待、采用仅当前 lease 的纯计算、调整通知对象，能移动部分 API 时间，但没有让整帧准备赶上下一边界。
4. S3 的标准 AHB-GDMA 允许访问 PSRAM；执行器原型使用公开 `esp_async_memcpy` 接口，并确实执行了硬件拷贝。16 字节突发更慢；32／64 字节突发仍未使双 PARTIAL 超过约 30。硬件执行次数不能替代吞吐收益证据，该原型未合入。

## 被排除的候选

- 同步 CPU copy、逐行 memcpy、tile 后写回缓存，以及这些操作的组合。
- 仅在存在等待者时通知 ticket、仅关闭时通知 idle、绘制期间只通知生产者。
- 调整 copy worker 初始优先级、分核对照、CPU 拷贝移出 IRAM。
- 减少执行器重复 probe、内置 CPU 路径缩短、lease 行数计算快路径。
- 将 driver-owned FB 的缓存维护完全交给标准驱动，移除 adapter 重复写回。
- 标准 AHB-GDMA 的多种突发长度。

个别候选减少了某段等待，但 S3 双 PARTIAL 仍停留在约 33 ms 的帧节拍。部分候选还改变了控制同步或调度策略，缺少吞吐收益时没有理由增加这些复杂度。隔离组件已恢复为生产源码，候选仅保留在证据目录供审查。

## 尚未完成

剩余问题仍需修复。当前证据只确认：在相同数据量下，新路径没有达到 V1 的帧准备时限；它没有证明一个可直接删除的额外等待点，也没有证明增加某个执行器就能解决问题。后续需围绕 FB tile 热路径的整段交接成本做实现级收敛，并重新验证停止、取消及缓冲所有权，而非继续把单项局部优化当成完整修复。
