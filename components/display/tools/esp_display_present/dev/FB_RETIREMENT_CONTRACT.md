## 驱动必须提供的事实

一次切换需在驱动内部原子关联 `(epoch, generation, target_fb)`。`generation` 对每次提交唯一，不能由回调发生时当前 FB 地址推断；`epoch` 在重启、重置或其他使原有传输事实失效的操作时变化。序号不可静默回绕。

退休事件至少包含 `(epoch, generation, retired_fb, selected_fb)`，并由驱动保证：

1. 对应该次提交的新 FB 已由硬件路径选中，且提交未被其他提交覆盖。
2. `retired_fb` 上由此扫描路径产生的所有实际读取已经结束，且在新的提交之前不会再被读取，包括预取和重启路径。
3. 事件与驱动内的选择、重启和提交关系有确定的同步顺序；重复、延迟派发和回调先于提交函数返回均允许，但事件内容不可被后续提交改写。
4. 不具备这些保证时不产生该退休事件；停止或恢复必须提供独立的硬件静止证明，不能凭超时或故障释放内存。

不同 FB 的指针匹配本身不解决 ABA；普通 `on_frame_buf_complete` 的回调时刻也不自动携带上述事实。候选事件可以早于 submit 返回，调用方需在提交结果确定前保留事件；如果驱动返回拒绝却又提供了匹配事件，按矛盾状态处理，不能按拒绝回收。提交结果不确定时，保留 buffer 并进入故障／恢复路径。

一个事件确认的前提是驱动契约成立，**不是**强制一次 EOF 或 VSYNC。相同 buffer 的 active-write／首帧初始化需单独定义，不沿用旧 FB 退休语义。

## 两条驱动路径的待验证点

以下基于复测使用的 IDF 版本，具体行号与版本绑定，修改前须重新核对。

- P4 DSI：`mipi_dsi_dma_trans_done_cb` 读取 `cur_fb_index` 并启用对应链表，`dpi_panel_draw_bitmap_2d` 设置 `cur_fb_index`。需要确定 DMA 完成的链表对应哪块 FB、选择和提交如何同步、链表启用后旧链表是否还可能被硬件访问，以及错误和 reset 如何失效已有代次。
- S3 RGB bounce：`lcd_rgb_panel_fill_bounce_buffer` 在拷完一帧后将 `bb_fb_index` 更新为 `cur_fb_index`，普通回调没有携带这些值。`lcd_rgb_panel_try_restart_transmission` 可能重置 bounce 位置并重新填充；需要证明旧 FB 不会在退休后被重启路径再次读取，且两类 ISR 与提交切换有一致的同步规则。

以当前实现不能假设“给回调附上 selected 指针”就满足上述契约。驱动改动应在隔离 IDF 副本中实现，覆盖编译和硬件验证后，再确定如何交付 IDF 依赖；未提供新能力的版本继续走现有双边界回退。

## 当前可执行模型及后续验收

[test_scanout_retirement_contract.py](tests/test_scanout_retirement_contract.py) 列举匹配、早到、重复、错误 FB、旧／未来代次、ABA、确定拒绝、结果不确定及重启失效。这只是供接口实现对照的模型；它不验证实际驱动原子性、锁、ISR 上下文和内存读取时序，也不覆盖相同 FB 特例和停止恢复实现。

实际实现需另外覆盖：并发提交与 ISR 的各个交错、被覆盖的提交、计数耗尽、回调解绑、关闭和停机，以及重启中已发生／未发生的切换。然后在 P4 和 S3 分别以低扰动记录验证最后读取早于写权限授予，覆盖压力和 restart；性能测试另行运行并保持现有基线条件。S3 tile 的 acquire 等待需独立分解，不能预设全部来自退休节拍。
